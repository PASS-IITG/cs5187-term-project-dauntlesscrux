# CVE revision and mechanism audit

## Corrected pairing

The 2022 and 2023 worktree HEADs are respectively the direct parents of their listed fixes: `8e257b86e5812c6e1cfa9e8e5f5660ac7bed899d` → `63bcf189be73a9cc1264059bed6f57974be74a83`, and `cbafa34b5a057794c5c08cd4657038e1f643c1ac` → `8818064ce3c3c0f1b740a5aaba2a987e75bfbafd`. The commit metadata and fix diffs were verified locally.

The CVE-2024-4741 worktree labelled vulnerable is at `b3f0eb0a295f58f16ba43ba99dad70d4ee5c437d`, whose commit subject is “Only free the read buffers if we're not using them” and whose message explicitly names CVE-2024-4741. Its parent is `ec559c2a6cca3fd4cedae5c47f2dfa38e5e24865`. The worktree labelled fixed is `2d05959073c4bf8803401668b9df85931a08e020`, a descendant of the official fix. Corrected temporary snapshots of `ec559c2` (vulnerable) and `b3f0eb0` (fixed) are in `/tmp/openssl-integrated-validation/`; original worktrees were not changed.

The official fix adds `RECORD_LAYER_data_present()` checks in `ssl/ssl_lib.c:5495-5496` and defines it in `ssl/record/rec_layer_s3.c:84-91`: it returns true for `rstate == SSL_ST_READ_BODY` or when `RECORD_LAYER_processed_read_pending()` is true. `SSL_free_buffers()` first checks `RECORD_LAYER_read_pending()` and `RECORD_LAYER_write_pending()` (`ssl/ssl_lib.c:5492-5493`), then after the fix rejects freeing on the two additional states before calling `RECORD_LAYER_release()` (`:5498`). `RECORD_LAYER_processed_read_pending()` counts processed/unread records (`rec_layer_s3.c:94-103`). These represent (1) a record header processed while its body is still arriving and (2) decrypted application data not fully consumed. The official advisory describes these two cases and says applications must call `SSL_free_buffers()` to be affected: https://www.openssl-library.org/news/vulnerabilities/ (accessed 2026-11-06).

## Invariant audit by CVE

- **CVE-2022-4450, PEM output lifetime:** On failure, `PEM_read_bio_ex()` must not leave caller-visible `header` or `data` pointing at freed output allocations. The fix commit adds NULL resets following frees in `crypto/pem/pem_lib.c`. OpenSSL's `test/pemtest.c:99-125` includes an empty-payload fixture (`-` base64 EOF), expects read failure, and frees the returned output pointers. The advisory confirms the empty-payload double-free mechanism: https://www.openssl-library.org/news/vulnerabilities-1.1.1/ (accessed 2026-11-06).
- **CVE-2023-0215, BIO chain ownership:** `BIO_push(asn_bio, out)` links the newly allocated filter into a caller-owned chain before `asn1_cb` runs. On callback failure, vulnerable `crypto/asn1/bio_ndef.c:99-102` frees `asn_bio` but does not detach it; fixed cleanup pops the tracked BIO before freeing. BIO_push/BIO_pop and BIO_free semantics are distinct: freeing the filter without restoring links can leave `out->prev_bio` dangling. The official advisory describes the invalid chain/UAF: https://www.openssl-library.org/news/vulnerabilities/ (accessed 2026-11-06).
- **CVE-2024-4741, read-buffer lifetime:** The invariant is conditional release: do not release a read buffer while a record body is incomplete or processed record data remains unread. The actual upstream fix is a precondition in `SSL_free_buffers()` with record-layer predicates. The Python checker instead inspects whether `ssl3_release_read_buffer()` resets `b->buf`, `packet` and `packet_length`; it does not inspect the `SSL_free_buffers()` precondition or call-state. Therefore it is a related stale-state heuristic, not a detector for this CVE mechanism. It will flag the official fixed `b3f0eb0` implementation because the local buffer helper was not changed by that commit. It can miss the CVE if a vulnerable release path resets pointers but still frees while record data is present.
